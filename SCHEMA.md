# CtxBeacon Event Schema

This document defines the schema for CtxBeacon's append-only JSONL ledger (`ledger.jsonl`).

Every line in the ledger is an independently valid, self-contained JSON object representing a discrete lifecycle event in the agent run.

---

## 1. Core Principles

- **Append-only:** Records are written sequentially and never mutated or silently rewritten.
- **Deterministic Hashing:** Cryptographic SHA-256 hashes record exact context and request payloads without capturing volatile authorization secrets.
- **Privacy First:** Raw credentials, API keys, and sensitive tokens are strictly excluded from event logs and hashes. Full message text snapshots are opt-in and stored separately under `ledger/snapshots/` (which is excluded from Git tracking).
- **Simulation Transparency:** Every synthetic, mock, or simulated event is marked explicitly with `"simulation": true`.

---

## 2. Common Fields

Every ledger event record contains the following mandatory fields:

| Field | Type | Description |
|---|---|---|
| `schema_version` | string | Current schema semantic version (e.g. `"1.0.0"`). |
| `event_id` | string | Unique event identifier (e.g. `"evt-3f8a9b2c1d0e"`). |
| `ts` | string | UTC ISO 8601 timestamp with `Z` timezone indicator (e.g. `"2026-10-22T10:00:00.000Z"`). |
| `run_id` | string | Unique execution run identifier (e.g. `"run-a1b2c3d4e5f6"`). |
| `turn` | integer \| null | Current agent interaction turn index (0-indexed), or `null` for run-level events. |
| `event_type` | string | Enumerated event type identifier (see Section 3). |
| `simulation` | boolean | `true` if event was generated by a mock, fixture, or simulation; `false` for genuine live API interactions. |
| `status` | string | Event outcome status (e.g. `"ok"`, `"error"`, `"blocked"`, `"completed"`). |

---

## 3. Event Types and Structures

### 3.1 `run_started`
Emitted when a new agent run initiates.

- **Required fields:** `task` (string)
- **Optional fields:** `system_prompt` (string), `model` (string), `provider` (string), `budget_tokens` (int), `threshold` (float)

### 3.2 `request_sent`
Emitted immediately before dispatching an HTTP or mock model request.

- **Required fields:**
  - `provider` (string, e.g. `"bharatcode"`, `"mock"`)
  - `model` (string, e.g. `"qwen-3.8-27b"`)
  - `request_hash` (string, SHA-256 hex digest of serialized request payload without secrets)
  - `context_hash` (string, SHA-256 hex digest of conversation messages)
- **Optional fields:** `estimated_context_tokens` (int), `token_count_method` (string)

### 3.3 `provider_response`
Emitted when a response is received from the provider.

- **Required fields:**
  - `provider` (string)
  - `model` (string)
  - `status_code` (int, e.g. 200, 429, 500)
  - `latency_ms` (int or float)
- **Optional fields:**
  - `provider_usage_tokens` (dict with `prompt_tokens`, `completion_tokens`, `total_tokens`)
  - `has_tool_calls` (boolean)
  - `tool_call_count` (int)
  - `retry_after_seconds` (int or float)
  - `reason` (string, e.g. error message)

### 3.4 `tool_call_started`
Emitted before a tool executes within the sandboxed environment.

- **Required fields:**
  - `tool_name` (string, e.g. `"write_file"`)
  - `tool_call_id` (string)
- **Optional fields:** `arguments` (dict)

### 3.5 `tool_call_completed`
Emitted after a tool finishes execution.

- **Required fields:**
  - `tool_name` (string)
  - `tool_call_id` (string)
  - `execution_status` (string, e.g. `"success"`, `"error"`, `"rejected"`)
- **Optional fields:** `output_preview` (string), `error` (string), `target_path` (string)

### 3.6 `compaction_started`
Emitted when the context token threshold is reached and summarization begins.

- **Required fields:**
  - `context_before_tokens` (int)
- **Optional fields:**
  - `token_count_method` (string)
  - `total_messages_before` (int)
  - `summarize_target_count` (int)

### 3.7 `compaction_completed`
Emitted when older messages have been summarized and the effective context rebuilt.

- **Required fields:**
  - `context_before_tokens` (int)
  - `context_after_tokens` (int)
  - `retained_ids` (array of string message IDs)
  - `dropped_ids` (array of string message IDs)
- **Optional fields:**
  - `token_count_method` (string)
  - `summary_ref` (string)
  - `snapshot_ref` (string or null)
  - `context_hash_before` (string)
  - `context_hash_after` (string)
  - `summary_preview` (string)

### 3.8 `provider_failover`
Emitted when switching from a primary provider/model to a fallback due to an error or rate limit.

- **Required fields:**
  - `from_provider` (string)
  - `to_provider` (string)
  - `reason` (string)
- **Optional fields:**
  - `from_model` (string)
  - `to_model` (string)
  - `status_code` (int)
  - `retry_after_seconds` (int or float)
  - `retry_attempt` (int)
  - `context_hash` (string)

### 3.9 `constraint_check`
Emitted after compaction or after a tool call to record deterministic constraint audits.

- **Required fields:**
  - `constraint_findings` (array of finding objects)
- **Finding object structure:**
  - `constraint`: string text of the original requirement
  - `status`: string (`"preserved"`, `"possibly_missing"`, `"possible_violation"`, `"violation_observed"`, `"unable_to_verify"`)
  - `marker_terms`: array of strings used for keyword matching
  - `matched_markers`: array of strings matched (or empty)
  - `evidence_message_id`: string message ID where constraint was originally introduced
  - `evidence_tool_call_id`: string tool call ID (if violation observed)
  - `details`: explanatory text

### 3.10 `run_completed`
Emitted when the agent terminates (task finished, turn limit reached, or error).

- **Required fields:**
  - `total_turns` (int)
- **Optional fields:**
  - `termination_reason` (string, e.g. `"completed"`, `"max_turns_reached"`, `"error"`)
  - `total_tool_calls` (int)
  - `compactions_performed` (int)

### 3.11 `request_blocked`
Emitted when an action or tool call is blocked due to safety or workspace boundaries.

- **Required fields:**
  - `reason` (string)
- **Optional fields:** `target_path` (string), `tool_name` (string)

---

## 4. Deterministic Hashes and Their Limitations

CtxBeacon computes two cryptographic SHA-256 hashes:

1. **`context_hash`**: Computed over the deterministically serialized JSON structure of the conversation messages (`role`, `content`, `tool_calls`, etc.).
2. **`request_hash`**: Computed over the application-side payload dispatched to the model provider, strictly stripping authorization keys and headers.

### Important Limitation Note
> **Payload Identity vs Attention:**
> A hash proves exact payload identity at the application boundary. It verifies the exact request constructed by CtxBeacon before dispatch.
> **It does not prove what a remote model internally attended to or retained in its weights or attention cache.**
